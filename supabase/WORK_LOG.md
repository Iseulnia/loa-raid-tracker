## 지금까지 구현된 기능

**인증**
- 처음엔 매직링크(OTP) → 이메일 확인 번거로움 때문에 이메일+비밀번호로 전환
- `allowed_emails` 테이블 기반 허용목록: 초대 안 된 이메일은 가입(트리거에서 예외 발생) 자체가 막힘 —
  실제 도메인에 배포하면서 "아무나 가입 가능" 문제를 막기 위해 추가
- 친구 초대 시 SQL Editor에서 `insert into public.allowed_emails (email) values ('...')` 먼저 실행 필요
- `/reset-password` 페이지로 비밀번호 재설정 지원 (로그인 화면 "비밀번호를 잊으셨나요?")
- 세션 유지기간(Time-box) 관련 논의는 했지만 **적용 안 하기로 결정** (사용자 요청)

**대시보드(`/`) — 개인 전용**
- 로그인한 사람의 캐릭터만 표시. 상단에 "남은 레이드 / 거래가능 골드 / 귀속 골드" 진행률 바
- "전투력 전체 갱신" / "전투력 전체 초기화" 버튼 (아래 설명) — 3시간 자동 갱신도 추가됨(아래)
- 원정대(expedition_label)별로 캐릭터 그룹핑, 그룹마다 대표 캐릭터(★) 표시 가능
- **캐릭터 카드 순서 + 원정대 순서를 직접 바꿀 수 있음** — "캐릭터 순서 변경" 버튼 → 팝업
  (`CharacterReorderModal.tsx`)에서 원정대 "안"의 캐릭터는 드래그로, 원정대 "자체" 순서는 화살표(▲▼)로
  바꿈 → `reorderCharacters` 액션으로 `characters.sort_order`를 배열 인덱스로 일괄 저장. 대시보드의 원정대
  그룹 순서도 그 안 최소 `sort_order` 기준으로 정렬됨
- 처음엔 원정대 그룹 순서를 아이템레벨 기준(본계>부계>부부계, 예전 방식)으로 고정했다가, "원정대 순서도
  바꿀 수 있게 해달라"는 요청으로 다시 sort_order 기준으로 바꿨음. 이번엔 **기존 sort_order가 최초 임포트
  시점 순서라 그대로 쓰면 순서가 뒤죽박죽되는 문제**를 `migration_2026-08-23a`로 먼저 해결함 — 지금 이
  순간의 기본 노출 순서(원정대는 최고 아이템레벨 내림차순, 캐릭터는 아이템레벨 내림차순)를 기준으로
  sort_order를 한 번 정규화해서, 아직 아무도 순서를 안 바꾼 상태에서는 화면이 예전과 똑같이 보이게 해둠.
  이후로는 사용자가 정한 순서가 그대로 유지됨. **캐릭터 드래그는 원정대 경계를 못 넘게 일부러 제한**해서
  (원정대 순서는 화살표 전용) 두 조작이 서로 꼬이지 않게 함
- **버그였던 것: 팝업에 뜨는 순서가 대시보드 순서와 다름** — `CharacterReorderModal`의 `buildGroups`가
  원정대 그룹을 라벨 알파벳순(`localeCompare`)으로 다시 정렬하고 있어서, 대시보드의 `groupByExpedition`(그룹
  내 최소 sort_order 기준)과 순서가 어긋나 헷갈린다는 피드백. 팝업에 들어오는 `characters` prop은 이미
  Dashboard에서 sort_order로 정렬해서 넘기므로, 별도로 재정렬하지 않고 그 순서 그대로 순회하며 그룹만
  나누도록 바꿈(첫 번째로 만나는 캐릭터가 자연히 그 그룹의 최소 sort_order가 되므로 대시보드와 동일한 결과).
  원정대 미지정 그룹만 대시보드처럼 항상 맨 뒤로 보냄
- **드래그 재배치 애니메이션 추가**: 네이티브 HTML5 드래그로 배열을 바로 바꾸면 항목이 순간이동하듯
  툭툭 끊겨 보인다는 피드백. 외부 라이브러리 없이 FLIP 기법(바뀌기 전 위치로 즉시 옮겨두고 다음 프레임에
  트랜지션 걸어서 제자리로 되돌림, `useLayoutEffect` + 각 `<li>` ref로 `getBoundingClientRect` 비교)으로
  부드럽게 밀리는 것처럼 보이게 함
- **버그였던 것: 애니메이션이 될 때도 있고 안 될 때도 있음** — 드래그 중엔 `dragover`가 아주 빠르게 여러 번
  발생해서, 이전 순서 변경의 200ms 트랜지션이 채 안 끝난 채로 다음 순서 변경이 들어오는 경우가 흔했음. 그
  상태에서 그냥 `getBoundingClientRect`를 재면 트랜지션 도중의 어중간한 위치를 "지금 자리"로 잘못 측정하게
  돼서 델타 계산이 틀어졌던 것. 매번 측정하기 전에 먼저 트랜지션 없이 transform을 확실히 지워서(+ 강제
  리플로우로 그 상태를 먼저 반영시킨 뒤 다음 프레임에 트랜지션), 항상 "진짜 배치된 자리"를 기준으로 계산하게
  고쳐서 연속으로 빠르게 드래그해도 매번 정확히 애니메이션되게 함
- **버그였던 것: 살짝만 옮겨도 위아래로 계속 왔다갔다함** — 대상 항목에 커서가 살짝만 걸쳐도 바로 자리를
  바꾸다 보니, 바뀌는 순간 원래 그 자리에 있던 항목이 커서 밑으로 오면서 다시 `dragover`가 걸려 원상복구
  → 다시 바뀜 → ... 이 반복되는 진동이 있었음(경계 근처에서 특히 심함). `handleDragOver`에서 커서가 대상
  항목의 세로 중간선을 실제로 넘어야만(아래로 옮기는 중이면 중간보다 아래, 위로 옮기는 중이면 중간보다
  위) 자리를 바꾸도록 여유(hysteresis)를 둬서 진동을 막음 — 흔한 드래그 정렬 UI 패턴
- **버그였던 것: 가끔 애니메이션이 두 번 재생됨** — 처음엔 직전 순서 변경에서 예약해둔
  `requestAnimationFrame` 콜백이 안 끝난 채로 다음 순서 변경이 들어와서 그런 줄 알고 `rafIdRef`로 이전
  예약을 취소하도록 고쳤는데도 재현됨. 근본 원인은 CSS `transition`을 수동으로 껐다 켜는 방식 자체의 한계로
  보임 — 드래그 중 `dragover`가 워낙 빠르게 여러 번 발생해서, 이전 트랜지션이 채 안 끝난 상태에서 또
  트랜지션을 걸고 벗기는 걸 반복하면 브라우저가 트랜지션 상태를 완전히 정리하지 못하고 얽히는 경우가 있는
  것으로 추정. **Web Animations API(`el.animate()`)로 전면 교체**해서 해결함 — 매번 이전 애니메이션
  인스턴스를 명시적으로 `cancel()`하는데, 취소된 WAAPI 애니메이션은 인라인 스타일을 전혀 남기지 않고 즉시
  원래 자리로 돌아가므로 다음 위치 측정이 항상 정확하고, CSS `transition` 프로퍼티를 직접 조작하지 않아서
  타이밍이 꼬일 여지 자체가 없어짐
- **레이드별 현황** 카드 신설 — 레이드 이름별로 **난이도별 완료 캐릭터 수**("나이트메어 4/4" 식)와 그
  레이드에서 받을 수 있는 골드 합계(거래가능/귀속)를 같이 표시. 처음엔 난이도를 합쳐서 하나의 수치로
  보여줬다가, 사용자가 준 로아 자체 "레이드별 현황" 패널 스크린샷을 참고해서 난이도별로 쪼개고 골드도
  추가함
- **버그였던 것: 공격대 탭에서도 항상 "내" 캐릭터 기준으로만 뜸** — 원래는 대시보드/공격대 둘 다에서
  모드와 무관하게 항상 currentUser 하나만 계산해서 프로필 목록 위에 카드 하나로 고정 노출했는데, 사용자가
  공격대 탭에서는 친구별로도 보고 싶다고 요청. `myRaidStatusByName`(currentUser 전용 단일 리스트)을
  `raidStatusByNameByOwner`(모든 캐릭터를 owner_id로 먼저 묶은 뒤 그 안에서 레이드 이름별로 집계하는
  `Map<ownerId, RaidStatusEntry[]>`)로 일반화하고, 카드 자체도 `RaidStatusByNameCard` 컴포넌트로 분리해서
  프로필 목록 위의 고정 카드 하나 대신 **사람별 섹션 안에, 그 사람의 접기/펼치기 상태(`collapsedProfiles`)를
  그대로 따르도록** 옮김 — 접으면 그 사람의 캐릭터 카드들과 함께 현황판도 같이 접힘. 제목은 본인이면 "내
  레이드별 현황" 그대로, 친구면 "{닉네임}의 레이드별 현황"으로 표시
- **버그였던 것**: 이 카드의 골드 합계가 클리어 여부와 상관없이 "숙제로 고른 전체" 기준이라, 체크를 해도
  숫자가 안 줄어들어서 확인하는 의미가 없다는 피드백을 받음. 캐릭터 카드 하단의 "받을 수 있는 골드"(아래
  참고)는 원래도 잔여량 기준이었는데 이 카드만 빠져 있었던 것 — **미클리어분만 합산**하도록 수정해서 체크할
  때마다 줄어들게 함. 다만 골드 종류(거래가능/귀속) 표시 자체는 "지금 남은 값"이 아니라 "원래 그 종류
  골드가 나오는 레이드였는지"로 판단(`everTradeable`/`everBound`) — 남은 값 기준으로 하면 마지막 레이드를
  체크하는 순간 조건이 바로 거짓이 되면서 애니메이션(아래 참고) 없이 통째로 사라져 보이는 문제가 있었음
- **전투력 3시간 자동 갱신**: localStorage에 마지막 자동 갱신 시각을 사용자별로 저장해뒀다가, 그만큼
  지났으면 페이지 열 때 자동으로 `refreshAllCombatPower` 실행 + 탭을 오래 켜두는 경우를 위해 3시간 간격
  타이머도 추가. 기존 수동 버튼은 그대로 둠

**공격대(`/party`) — 공용 탭**
- 모든 친구의 캐릭터/체크 현황을 친구별 박스로 모아서 봄. 내 캐릭터만 체크 가능, 남 캐릭터는 읽기 전용
- Dashboard 컴포넌트를 `mode="mine" | "party"` prop으로 재사용 (완전히 별도 컴포넌트 아님)
- **내 원정대가 항상 맨 위**로 오도록 프로필 목록을 정렬함 (전엔 등록 순이라 내 캐릭터가 아래쪽에 묻힐 수 있었음)
- **친구 이름을 클릭하면 그 사람의 캐릭터 목록이 접힘/펼쳐짐** (로컬 state, 새로고침하면 초기화됨 — 영구 저장은
  안 함)

**내 캐릭터(`/characters`)**
- 대표 캐릭터명 입력 → 로스트아크 오픈 API로 원정대(siblings) 전체 불러오기, 아이템레벨 상위 6개 기본 체크
- "원정대 이름" 입력 필수 (부계정/부부계정 구분용, expedition_label)
- 대표 캐릭터 지정(is_main_character), 골드 획득 캐릭터 여부 토글, 삭제

**숙제(레이드) 관리**
- 별도 "레이드 관리" 화면 없음 — 마스터 레이드 목록은 `schema.sql` 시드 데이터로만 관리, 패치 나오면
  직접 SQL 고쳐서 재실행 (앱 내 편집 UI 없음, 의도적으로 그렇게 함)
- 캐릭터별 숙제 선택은 대시보드의 "숙제 편집" 팝업(HomeworkEditor)에서: 레이드 이름별로 난이도 하나만 선택,
  "골드 최대화 자동 선택"(거래가능 기준/총골드 기준 중 선택) 버튼 있음
- **골드 획득 레이드는 캐릭터당 최대 3개** — 예전엔 자동(골드 높은 순)이었다가, **사용자가 직접 고르는 방식으로
  변경**함 (숙제 편집에서 레이드 고를 때마다 "골드 받기" 토글)
- 레벨 미달 레이드는 숙제 편집에서 아예 선택 불가

**골드 계산 규칙 (`src/lib/raidDisplay.ts`)**
- 귀속/거래가능 분할: **성당(전체 단계) 100% 귀속**, **4막·종막·세르카는 노말만 절반 귀속+절반 거래가능**,
  그 외(벨가르딘 등)는 전부 거래가능. 이건 사용자가 실제 게임 기준으로 알려준 값이라 정확함
- 대시보드 상단 요약은 "획득한 골드 / 총 획득 가능 골드 (%)" 형식, 체크해도 총량은 안 변함
- 캐릭터 카드 하단 "받을 수 있는 골드"는 반대로 **체크할수록 줄어드는** 잔여량 표시 (의도적으로 다른 방식).
  "내 레이드별 현황" 카드의 골드도 이후 같은 방식(잔여량)으로 통일함

**숫자/체크 애니메이션 (`src/components/AnimatedNumber.tsx`)**
- 체크해서 레이드가 회색으로 음영 처리될 때 색이 뚝 끊겨 바뀌던 걸, 버튼/체크박스/텍스트에
  `transition-colors duration-300`을 넣어서 부드럽게 바뀌도록 함
- 골드/개수 숫자가 바뀔 때(체크·해제, 숙제 편집 등으로 총량이 바뀔 때) 값이 순간이동하지 않고 이전 값에서
  새 값까지 부드럽게 세는 것처럼 보이도록 `AnimatedNumber` 컴포넌트 신설 (매 프레임 `requestAnimationFrame`로
  ease-out 보간, 500ms). 대시보드 상단 요약, 내 레이드별 현황, 캐릭터 카드 잔여 골드 등 숫자가 바뀌는 모든
  곳에 적용. 진행률 바(width)는 별도 애니메이션 없이 CSS `transition-[width]`로 처리
- 값이 0이 되면 사라지는 조건부 렌더링과 숫자 애니메이션을 같이 쓰면, 실제 값이 0으로 바뀌는 즉시 DOM이
  통째로 사라져서 숫자가 줄어드는 모습을 볼 새도 없이 없어지는 문제가 있음 — 그런 곳은 "지금 값이 0인지"가
  아니라 "애초에 이 항목이 존재할 수 있는지"로 노출 조건을 따로 둬서 애니메이션이 끝까지 보이게 함
- **버그였던 것: 체크를 빠르게 두 번(체크→해제) 누르면 잠깐 뒤에 다시 체크된 상태로 돌아옴**. `toggle`이
  `setRaidCheck` 서버 액션을 매번 그냥 fire-and-forget으로 날렸는데, 두 요청이 순서 보장 없이 따로
  나가다 보니 네트워크 타이밍에 따라 "해제" 요청이 "체크" 요청보다 서버에 먼저 도착할 수 있었음(둘 다
  독립된 HTTP 요청이라 클라이언트에서 나중에 보냈다고 서버에 나중에 도착한다는 보장이 없음) — 그러면 최종
  DB 상태는 체크된 채로 남고, 뒤늦게 도착한 Realtime INSERT 이벤트 때문에 화면에서 체크가 사라졌다가 다시
  나타나는 것처럼 보였음. `(character,raid,gate)` 키별로 이전 요청이 끝난 뒤에만 다음 요청을 보내도록 promise
  체인을 걸어서 항상 사용자가 누른 순서대로 서버에 도착하게 고침. 이 체인은 컴포넌트 렌더와 무관하게
  요청 순서만 지키면 되는 값이라 `useRef`가 아니라 모듈 스코프 `Map`에 둠 — 처음엔 `useRef`로 만들었다가
  Next 16의 `react-hooks/refs` 린트 규칙("ref는 렌더 중이 아니라 이벤트 핸들러/이펙트에서만 접근해야 함")에
  걸렸는데, `toggle`이 실제로는 onClick에서만 호출됨에도 별도로 선언된 함수를 통해 간접 호출되는 형태라
  정적 분석이 안전하다고 확신을 못 한 것으로 보임 — 어차피 렌더링과 무관한 값이라 ref로 감쌀 필요가
  없었으므로 모듈 스코프로 옮겨서 근본적으로 해결함

**전투력 관리 (카오스던전 세팅 vs 레이드 세팅 문제)**
- 로스트아크는 카던 세팅/레이드 세팅이 따로 있어서 API 스냅샷 시점에 카던 세팅이면 전투력이 낮게 잡힘
- 그래서 DB엔 **역대 최고 전투력만** 저장 (`refreshAllCombatPower`: 새 값이 기존보다 높을 때만 갱신)
- "전투력 전체 초기화"(`resetAllCombatPower`)는 최댓값 비교 없이 강제로 현재 API 값 덮어씀 (스펙 다운 대응용)
- 이 버튼들은 캐릭터별이 아니라 **대시보드 상단에 전체 일괄 버튼 2개**로만 존재 (처음엔 캐릭터별로
  만들었다가 사용자 요청으로 대시보드 전체 버튼으로 이동)
- **버그였던 것: "전투력 전체 갱신"을 눌러도 아이템 레벨(캐릭터 카드의 "Lv.")은 안 바뀜** —
  `fetchCombatPower`가 로스트아크 API의 "프로필 조회" 응답에서 `CombatPower`만 꺼내 쓰고 있었는데, 같은
  응답에 `ItemAvgLevel`도 이미 들어있었음(다른 API 호출을 추가할 필요가 없었음). `fetchCombatPower`가
  `{ combatPower, itemLevel }`을 함께 반환하도록 바꾸고, `refreshAllCombatPower`/`resetAllCombatPower`
  둘 다 `item_level`도 같이 갱신하도록 함 — 아이템 레벨도 카던/레이드 세팅에 따라 순간적으로 낮게 잡힐 수
  있는 건 전투력과 같은 이유라서, "갱신"은 전투력과 동일하게 더 높을 때만 갱신, "초기화"는 최댓값 비교 없이
  강제로 덮어쓰는 규칙을 그대로 따름

**자동 감지(`/auto-detect`, 베타) — 픽셀 비교 → OCR로 최종 전환함**
- 처음엔 화면공유 라이브 프레임을 레이드×난이도별 "결과화면" 기준 이미지 14장과 픽셀 유사도 비교하는

  임계값 82%→88%, margin, 연속 2번 확인까지 다 넣어봤는데도 **벨가르딘 나이트메어와 종막 하드처럼
  배경/체크마크가 비슷한 화면끼리 계속 서로 오인식**했음(양방향으로 다 발생) — 두 번 튜닝해도 안 고쳐져서
  근본적으로 픽셀 비교로는 한계가 있다고 판단, **결과화면 텍스트(레이드명+난이도)를 OCR로 직접 읽는 방식으로
  전면 전환**함 (`src/lib/ocrMatch.ts`의 `matchRaidFromText` — 레이드 이름과 난이도가 텍스트에 둘 다
  포함돼야 매칭으로 인정, 하나만 맞으면 오탐 위험이 커서 일부러 엄격하게 함)
- OCR 전환 후 캡처 방식도 확 단순해짐: 레이드×난이도별 이미지 14장이 필요 없어지고, **결과화면 텍스트가
  뜨는 위치를 한 번만 등록**하면 모든 레이드에 재사용됨 (`result_screen_ocr` 템플릿 타입, 위치 고정이라
  캐릭터 이름 인식과 마찬가지로 슬라이딩 검색 불필요, `created_by`로 내가 등록한 것만 사용)
- OCR은 픽셀 비교보다 느려서 스캔 간격을 1.2초→1.5초로 늘리고, `ocrBusyRef`로 이전 인식이 안 끝났으면
  겹쳐서 안 돌게 함. 연속 2번 확인(CONFIRM_SCANS)은 그대로 유지(단일 프레임 오독 방지) — 이후 실사용에서
  문제 되어 아래에서 다시 조정함
- 디버그 표시도 "유사도 %" 대신 **"최근 인식된 텍스트"**를 그대로 보여주도록 바꿔서, OCR이 정확히 뭘
  읽었는지 바로 확인 가능함
- **OCR 인식률 개선**: 원본 픽셀을 그대로 tesseract에 넘기고 있었는데, 그레이스케일+대비 스트레칭 전처리
  (`enhanceContrast`, min~max를 0~255로 늘림)를 추가하고 최소 업스케일 폭도 240px→320px로 올림. 또한
  기본 PSM(문서용 자동 레이아웃 분석)이 한 줄짜리 UI 라벨엔 안 맞아서, 캐릭터 이름/결과화면 텍스트는
  `SINGLE_LINE`, 참여현황 패널(아이콘으로 끊긴 여러 줄)은 `SPARSE_TEXT`로 명시적으로 지정함
  (`worker.setParameters`, 같은 워커를 공유하므로 호출 직전마다 필요한 모드로 맞춤) — 이후
  `SINGLE_LINE`은 아래에서 `SINGLE_BLOCK`으로 다시 바꿈
- **버그였던 것: 레이드에 따라 결과화면에서 레이드명과 난이도가 서로 다른 줄에 나오면 인식이 깨짐** —
  세르카 레이드는 "고통의 마녀, 세르카"와 "[나이트메어]"가 2줄로 나뉘어 나오는데(대부분의 다른 레이드는
  "종막 : 최후의 날 [하드]"처럼 한 줄), 사용자가 등록한 크롭이 이 2줄 + 체크마크 아이콘 + "나가기" 버튼까지
  포함하고 있었음. `recognizeRegionText`가 "이 영역은 한 줄짜리 텍스트"라고 가정하는 `SINGLE_LINE` 모드를
  쓰고 있어서, 실제로는 여러 줄/여러 요소가 섞인 크롭을 억지로 한 줄로 읽으려다 줄이 뒤섞이거나 글자가
  깨지는 문제가 있었음(앞서 봤던 "이상한 텍스트" 잡음의 원인 중 하나로 추정). 사용자마다 등록하는 크롭
  모양이 완전히 똑같을 수 없어서, `SINGLE_LINE` 대신 한 줄이든 여러 줄이든 "하나의 균일한 텍스트 블록"으로
  보는 `SINGLE_BLOCK`으로 바꿔서 둘 다 안정적으로 읽히게 함
- **설계 실수였던 것: 레이드명+난이도만으로는 애초에 클리어 여부를 판단할 수 없었음** — 처음엔 "그 위치에
  레이드명+난이도 텍스트가 뜨면 클리어된 결과화면"이라고 가정하고 만들었는데, 사용자가 실제 게임 화면
  기준으로 정정해줌: 관문 제목 표시줄의 레이드명·난이도는 **입장 직후부터 클리어 여부와 상관없이 항상
  떠 있고**, 실제로 클리어했을 때만 바뀌는 건 그 아래 버튼이 "나가기"로 바뀌는 것(화면 중앙에 별도로
  "던전 클리어" 텍스트가 뜨는 것도 대안으로 있었는데, 사용자가 "나가기" 버튼 쪽으로 확정함). 그래서
  `matchRaidFromText`가 이름+난이도만 맞으면 바로 매칭시켜버려서, 사실상 관문 입장 시점부터 계속
  오탐(클리어 안 했는데 클리어로 체크) 위험이 있는 구조였음. 사용자가 이미 등록해둔 크롭이 마침
  제목+체크마크+나가기 버튼까지 다 포함하고 있어서(원래는 "체크마크/버튼은 빼고 텍스트만 좁게" 등록하라고
  잘못 안내했었는데, 이 사실이 밝혀지면서 안내를 정정함 — 오히려 나가기 버튼까지 포함해야 함), 새 크롭을
  따로 등록할 필요 없이 매칭 조건에 `CLEAR_BUTTON_TEXT`("나가기")가 텍스트에 같이 포함돼야 한다는 조건만
  추가해서 고침
- **난이도 별칭**: 일부 레이드는 화면에 난이도가 "노말"이 아니라 "싱글 모드"로 표시됨(사용자 확인: 컨텐츠
  자체는 노말과 동일). DB의 난이도 값은 그대로 "노말"로 두고, `matchRaidFromText`의 난이도 비교에서만
  "싱글모드"를 "노말"의 별칭으로 같이 인정하도록 `DIFFICULTY_ALIASES`를 추가함(DB 스키마/시드 데이터는
  안 건드림)
- **인식 영역 디버그 오버레이 추가**: OCR이 계속 이상한 텍스트(레이드 제목이 아니라 다른 UI 요소로 보이는
  잡음)를 읽는다는 제보를 받았는데, 화면공유 미리보기만으로는 등록한 크롭이 실제로 어디를 가리키는지 눈으로
  확인할 방법이 없었음. 스캔 중 비디오 위에 지금 쓰이는 `resultScreenOcrRegion`/`characterNameRegion`을
  퍼센트 좌표 그대로 겹쳐서 박스로 그려주도록 추가함(`ScreenCapture.tsx`의 선택 영역 표시와 같은 방식) —
  이제 실제 게임 요소와 크롭이 잘 맞는지 스캔 중에 바로 눈으로 검증 가능
- 이 과정에서 발견한 것: `result_screen_ocr` 템플릿을 사용자가 레이드마다(세르카, 구원의 종탑) 하나씩 총
  2개 등록해뒀는데, 코드는 **가장 최근 것 하나만**(`.find()`) 실제로 사용함 — 위치가 모든 레이드에서
  항상 같은 자리라는 게 이 기능의 전제라 원래 하나만 등록하면 충분한데, 예전 픽셀 비교 방식(레이드마다
  기준 이미지 필요)의 사용 습관이 남아있었던 것으로 보임. 안내 문구를 "레이드별로 여러 개 등록할 필요

  알려준 힌트대로, 레이드 중에는 항상 화면 우측 파티원 목록 맨 위에 내 캐릭터가 표시되므로 그 위치 하나만
  OCR로 읽으면 됨. 새 템플릿 타입 `party_top_name_ocr` 추가(메뉴 감지의 `character_name`은 캐릭터 선택
  메뉴 화면 기준으로 등록하는 거라 레이드 중 다른 레이아웃 화면에는 못 씀 — 그래서 따로 만듦). 메뉴
  감지(`StatusPanelScanner`)의 `verifyCharacter` + `characterLockedRef`(수동 선택 시 자동 인식이 안
  덮어쓰게) 패턴을 그대로 가져와서, 결과화면 OCR과 같은 스캔 틱 안에서 캐릭터도 같이 재확인함(따로 타이머를
  돌리면 그 텀 사이에 레이드가 끝나버릴 경우 이전 캐릭터로 잘못 체크되는 문제가 있어서 처음부터 병합해둠).
  등록 안 해도 기존처럼 드롭다운으로 직접 고르면 되는 선택 기능
- **버그였던 것(위 캐릭터 자동 인식 추가하면서 잠재돼 있던 것): 인터벌이 캐릭터 자동 인식으로 바뀐
  selectedCharacterId를 못 따라갈 뻔함** — `setInterval(runScan, ...)`이 `startShare()` 호출 시점의
  `runScan` 클로저(그 시점의 `selectedCharacterId` state)를 그대로 붙잡고 있는데, 캐릭터 자동 인식이 스캔
  도중 state를 바꾸면 인터벌은 계속 옛 값을 참조하게 됨(메뉴 감지에서 이미 겪었던 stale closure 문제와
  동일). `selectedCharacterIdRef` + `runScanRef`(매 렌더마다 최신 함수로 갱신, 인터벌은 이 ref로만 호출)로
  고쳐서 처음부터 재발 안 하게 만듦
- "던전 클리어" 배너/관문 체크마크 템플릿(clear_banner/gate_checkmark)은 애초에 참고용으로만 저장 가능하고
  실제 매칭엔 안 썼는데, 이번에 캡처 UI에서도 아예 제거함(선택지가 result_screen_ocr 하나뿐)
- 초기화(reset) 버튼은 캐릭터별로 있고, 자동 체크된 항목은 "취소" 가능
- **버그였던 것(픽셀 비교 시절)**: 템플릿 이미지가 Supabase Storage(다른 origin)에서 오는데 `crossOrigin`
  설정이 없어서 캔버스가 오염돼(`getImageData`가 SecurityError) 유사도 비교가 매 스캔 조용히 실패하던 문제.
  `ScreenCapture.tsx`의 "지금 프레임 캡처"도 캔버스가 `{frozen && ...}` 안에만 마운트돼 있어서(캡처 버튼이
  그 캔버스에 그려야 frozen이 true가 되는데 버튼 누를 땐 아직 없어서 조용히 no-op) 버튼이 아예 안 먹혔던
  실제 버그였음 — 캔버스를 항상 마운트(안 보일 때만 CSS로 숨김)하도록 수정 (이 버그 자체는 OCR 전환과
  무관하게 지금도 유효한 수정사항)

**참여현황 패널 스캔 (`/menu-detect` 탭, `StatusPanelScanner.tsx`, `src/lib/ocrMatch.ts`)**
- 처음엔 `/auto-detect` 페이지 안에 같이 넣었다가, **사용자 요청으로 완전히 별도 탭("메뉴 감지")으로 분리**함
  — `/auto-detect` 탭은 이 기능 추가 이전과 100% 동일하게 되돌림. 이를 위해 `ScreenCapture.tsx`에
  `allowedTypes` prop을 추가해서 탭마다 고를 수 있는 기준 이미지 유형을 제한함
- **레이드 인식도 최종적으로 OCR로 감**: 처음엔 레이드별 이름표 이미지를 세로 슬라이딩 윈도우로 찾고(`rowScan.ts`,
  이제 삭제됨) 배지는 초록 픽셀 비율로 판정하는 방식이었는데, 레이드마다 이름표+배지를 따로 등록해야 하는
  번거로움 + 자동 감지 탭에서 픽셀 비교가 결국 실패한 전례 때문에 **참여현황 패널 전체를 통째로 OCR로 읽는
  방식으로 전환**함 (`recognizeParticipationPanel`). 패널 영역을 한 번만 등록해두면, 매 스캔마다 그 안의 모든
  줄을 한꺼번에 읽어서 등록된 레이드 이름들이 몇 번째 줄에 있는지 찾고, 그 줄과 세로 위치가 가까운 곳에
  "완료"라는 글자가 있으면 클리어로 판정함 (tesseract가 이름과 상태 배지를 같은 줄로 묶든 아이콘 때문에
  다른 줄로 쪼개든 상관없이, 세로 위치 근접도로 상관관계를 봐서 둘 다 대응함) — 아직 실사용 검증 전이라
  줄 세그멘테이션이 예상과 다르게 나오면 튜닝 필요할 수 있음
- `raid_clear_templates`에 `template_type='participation_panel_ocr'` 신설 (예전 `status_row` 타입은 이제
  안 씀, 레거시 행은 DB에 남아있을 수 있지만 매칭에 안 쓰임)
- 결과화면 자동감지처럼 상시 켜두는 방식이면 렉 문제가 있다는 사용자 피드백 → **수동 시작/종료 버튼** 방식으로
  설계 (패널 열고 스캔 시작 → 천천히 스크롤하며 실시간 인식 목록 확인 → 스캔 종료)
- **캐릭터 자동 인식도 이미지 매칭 → OCR로 전환함**: 캐릭터별로 이름표 이미지를 등록하는 대신, 이름이 뜨는
  화면 자리를 **딱 한 번만** 등록해두면(캐릭터별 등록 불필요) 스캔 시작 시 그 영역 글자를 OCR로 읽어서
  (`recognizeRegionText`) 내 캐릭터 이름 목록과 편집거리 기준으로 매칭함(`matchCharacterName`). 자동 인식은
  선택 사항 — 안 등록해도 수동 드롭다운으로 동작하고, 스캔 중 드롭다운을 직접 바꾸면 자동 인식이 안 덮어씀
- OCR 관련 위치 지정 템플릿(`character_name`, `participation_panel_ocr`)은 **내가 캡처한 것만** 쓰도록
  `created_by`로 한정함 — `raid_clear_templates`가 RLS상 로그인한 모두에게 보이는 테이블이라, 필터링 안
  하면 다른 사람의 화면 배치/해상도 기준 좌표가 섞여 들어와서 엉뚱한 위치를 읽게 됨
- **한 스캔 세션에서 여러 캐릭터 연속 처리 지원**: 캐릭터 OCR을 스캔 시작 시 한 번만이 아니라 2.5초 간격으로
  계속 재시도해서, 스캔 도중 게임에서 다른 캐릭터로 전환해도 자동으로 따라감. `foundKeysRef`/`found` 목록도
  `raidLabel` 단독 키가 아니라 `characterId:raidLabel` 복합 키로 관리해서, 캐릭터를 전환해도 이전 캐릭터의
  처리 상태와 안 섞이고 나중에 같은 캐릭터로 돌아와도 중복 처리 안 됨. 목록에도 캐릭터 이름을 같이 표시함
  ("키츠네아 · 벨가르딘")
- setRaidCheck으로 체크된 항목엔 취소 버튼 추가 (오탐 대응). 취소해도 게임 화면 배지는 그대로 "참여
  완료"라서, 같은 세션 동안은 재감지 대상에서 제외해 곧바로 다시 체크되는 걸 막음. 레이드 이름만 인식되고
  아직 클리어 상태가 아니면 "클리어 X"로 목록에 표시해서 스캔이 제대로 보고 있는지 확인 가능하게 함
- **체크 실패(React #441)의 진짜 원인 — weekly_checks에 UPDATE RLS 정책이 아예 없었음**: 클리어로 인식된
  레이드마다 "체크 실패: React #441"이 반복 재현돼서 여러 라운드에 걸쳐 다른 원인들을 의심하고 고쳤음
  (① `selectedCharacterIdRef`가 useEffect로 비동기 갱신되는 경쟁 상태 → 동기 갱신으로 수정, ② 한 틱에
  레이드 여러 개가 동시에 클리어로 잡히면 setRaidCheck가 병렬로 여러 번 날아가던 것 → 순차 처리로 수정,
  ③ setInterval 콜백이 startScan() 시점의 낡은 클로저를 계속 참조하던 것 → ref로 항상 최신 함수를 참조하도록
  수정). 셋 다 실제로 있던 문제라 고칠 가치는 있었지만, **진짜 원인은 따로 있었음**: `setRaidCheck`이
  upsert를 쓰는데, 이미 존재하는 (캐릭터,레이드,관문,주차) 행에 대해서는 upsert가 내부적으로
  `ON CONFLICT DO UPDATE`로 UPDATE를 시도한다. 그런데 `weekly_checks`엔 SELECT/INSERT/DELETE 정책만 있고
  **UPDATE 정책이 하나도 없어서**, RLS가 켜진 상태에서 UPDATE는 기본적으로 전부 거부되고 있었음 — "이미 한
  번이라도 체크된 적 있는 (캐릭터,레이드) 조합을 다시 체크"하려는 시도만 골라서 실패했던 것 (에러 메시지의
  "(USING expression)"이 결정적 단서였음 — INSERT 정책은 WITH CHECK를 쓰고 USING은 UPDATE/DELETE/SELECT
  정책에서만 씀). 소유권 확인(`character.owner_id` = `auth.uid()`)까지 직접 로그로 대조해서 완전히 일치하는
  걸 확인한 뒤에야 이 결론에 도달함 → `checks_update_own_character` UPDATE 정책 추가로 해결
  (`migration_2026-08-22o`). 참고로 Dashboard/AutoDetectRunner의 수동 체크가 항상 잘 됐던 이유는, 그쪽에서
  테스트한 조합들이 우연히 매번 "처음 체크하는" 상황(순수 INSERT)이었기 때문 — 이 버그는 오직 "이미 체크된
  걸 다시 체크"하는 경우에만 재현됨
- 업로드 경로에 한글(레이드 이름)을 그대로 넣었다가 Supabase Storage 키 검증에서 거부(Invalid key)당한 적
  있음 → 경로는 항상 ASCII만 쓰고, 실제 이름은 DB 컬럼에만 저장하도록 수정함 (이후 이런 템플릿류 경로 만들 때
  항상 주의)

### 탭 이동 속도 개선 — 중복 인증 확인 제거

- **문제**: 대시보드/공격대 등 탭을 클릭할 때마다 다른 사이트보다 눈에 띄게 느리다는 피드백. 원인은
  `supabase.auth.getUser()` 호출 — 이건 매번 Supabase Auth 서버에 네트워크로 토큰을 검증하는 요청을
  보낸다(로컬에서 바로 판단 안 함). 그런데 탭 하나 이동할 때마다 이게 **세 번** 일어나고 있었음:
  1. `src/proxy.ts`(Next.js 미들웨어)가 모든 요청마다 `updateSession`에서 한 번
  2. 루트 레이아웃에 항상 렌더링되는 `NavBar`가 한 번 더
  3. 그 페이지 자신(`page.tsx` 등)이 또 한 번
- **바뀐 것**: 미들웨어의 `getUser()`는 보안상 그대로 두고(여기서만 실제로 세션이 유효한지 네트워크로
  검증하고, 무효하면 `/login`으로 리다이렉트함), `NavBar`와 모든 페이지 컴포넌트(`page.tsx`, `party`,
  `characters`, `loa-tools`, `auto-detect`, `menu-detect`)는 `getUser()` 대신 `getSession()`으로 바꿈.
  `getSession()`은 쿠키에 이미 저장된 세션을 네트워크 호출 없이 그대로 디코드해서 반환하는 방식이라
  즉시 끝남 — 미들웨어가 이미 그 요청을 검증한 뒤에만 여기 코드가 실행되는 구조라서 안전함(Supabase도
  "미들웨어가 모든 라우트를 보호하는 게 보장되면 그 뒤에서는 `getSession()`을 써도 된다"고 함).
  결과적으로 탭 이동당 네트워크 인증 요청이 3번 → 1번으로 줄어듦.
- **일부러 안 건드린 것**: `actions.ts`(서버 액션)와 `api/lostark/*` 라우트는 그대로 `getUser()` 유지함 —
  이쪽은 탭 이동보다 호출 빈도가 훨씬 낮고(버튼 클릭 시에만), 데이터를 쓰는(mutate) 경로라 조금 더 보수적인
  검증을 유지하는 쪽을 택함. 체감 속도 문제의 원인은 아니었음.

### 탭 이동 시 로딩 표시 추가

- **문제**: 인증 확인 중복 제거로 실제 지연은 줄였지만, 여전히 다른 사이트처럼 "로딩이 도는" 느낌 없이

### 전체 코드 효율화/메모리 점검 (일반 목적 서브에이전트로 재감사)

이전 세션에서 한 번 메모리 누수 점검을 했지만 그 뒤로 로아 도구/더보기 효율/탭 재구성 등 코드가 많이
늘어서, 신규 코드 포함 전체를 다시 훑어달라고 서브에이전트에게 맡기고 그 결과 중 실제로 조치할 가치가
있는 항목만 골라 반영함.

- **tesseract.js 워커가 절대 안 꺼지던 문제**(`src/lib/ocrMatch.ts`): 워커를 모듈 스코프 싱글턴으로
  캐싱해서 재사용하는 건 의도된 설계(재초기화에 몇 초 걸림)지만, 그 결과 자동 감지/메뉴 감지 탭을 한 번만
  켜봐도 브라우저 탭이 열려있는 내내 WASM 워커가 메모리에 남아있었음. 5분간 인식 요청이 없으면 자동으로
  `terminate()`하는 idle 타이머를 추가함(`getWorker()` 호출마다 타이머 리셋) — 게임을 켜놓고 오래 쓰는
  앱 특성상 안 쓰는 동안 메모리를 계속 붙잡고 있을 이유가 없음. 다시 필요해지면 그때 새로 띄움.
- **캐릭터 이름 재인식 시 불필요한 4K 프레임 전체 복사**(`AutoDetectRunner.tsx`, `StatusPanelScanner.tsx`
  의 `verifyCharacter()`): 캐릭터 이름 한 번 인식할 때마다 `video.videoWidth × videoHeight`(최대
  3840×2160) 크기의 캔버스를 새로 만들어 비디오 프레임 전체를 그린 다음, 그중 극히 일부(캐릭터 이름
  영역)만 잘라서 썼음. `recognizeRegionText`는 `CanvasImageSource`를 받아서 video 엘리먼트를 직접 넘길
  수 있으므로, 중간 캔버스를 없애고 video를 바로 넘기게 바꿈 — 내부에서 크롭 영역 크기만큼만 그려져서
  불필요한 전체 프레임 복사가 없어짐. (메인 스캔용 캔버스는 같은 프레임에서 여러 영역을 순차로 읽어야 해서
  그대로 캔버스 방식 유지 — 이것까지 video로 바꾸면 두 영역이 서로 다른 프레임을 읽을 위험이 있음.)
- **등록된 기준 영역마다 서명 URL을 개별 요청하던 것**(`auto-detect/page.tsx`, `menu-detect/page.tsx`):
  `createSignedUrl`을 템플릿 개수만큼 병렬 호출하던 걸 `createSignedUrls`(복수형, 경로 배열을 한 번에
  서명)로 바꿔서 요청 횟수를 줄임. 템플릿 수가 보통 적어 체감 효과는 크지 않지만 코드도 더 단순해짐.
- **손대지 않은 것**: 화면공유 OCR 스캔 주기(0.8~2초), tesseract PSM 모드, Realtime 채널 구독/해제,
  MediaStream 정리 등은 이미 정상 동작 중이라 그대로 둠. 대시보드/공격대 페이지의 쿼리 중복(둘 다 비슷한
  5개 쿼리)과 캐릭터 순서 저장의 개별 UPDATE는 실질적 성능 영향이 미미하다고 판단해 지금은 손대지 않음
  (나중에 관련 코드를 만질 일이 생기면 같이 정리하는 정도로 충분).

### 레이드별 현황 난이도 배지로 캐릭터 목록 필터링

- **바뀐 것**: "레이드별 현황" 카드의 난이도 배지(예: "하드 2/5")를 누르면, 그 아래 캐릭터 목록이 그
  레이드+난이도를 숙제로 고른 캐릭터만 남도록 필터링됨. 다른 난이도를 누르면 그쪽으로 필터가 바뀌고,
  같은 배지를 한 번 더 누르면 필터가 풀리고 전체 캐릭터가 다시 보임(요청하신 토글 동작 그대로).
  공격대 탭에서는 사람마다 카드가 따로 있어서, 필터도 `profileId` 기준으로 각자 독립적으로 동작함(내
  카드에서 필터를 걸어도 친구 카드는 영향 없음). 필터가 걸려있을 때는 "OO 가는 캐릭터만 보는 중 · 전체
  캐릭터 보기" 링크를 캐릭터 목록 위에 띄워서 지금 필터링된 상태라는 걸 알 수 있게 하고, 바로 해제할 수
  있게 함(같은 배지를 다시 찾아 눌러야만 해제되는 건 UX상 불친절해서 추가한 보조 동선).

- **추가 수정**: 처음엔 "그 레이드+난이도를 숙제로 고른 캐릭터 전체"를 보여줬는데, 실제 용도가 "누가
  아직 이번 주에 안 갔는지 확인"이라는 피드백을 받고 필터 조건에 `!isRaidClearedAtAll(c.id, r)`를 추가해서
  이미 체크된 캐릭터는 목록에서 빠지게 함(체크하는 순간 실시간으로 목록에서도 사라짐). 안내 문구도
  "가는 캐릭터만 보는 중"에서 "미체크 캐릭터만 보는 중"으로 바꿔서 실제 동작과 맞춤.

### "미리보기 없음" 더미 기준 이미지 원인 규명 및 수정

사용자가 자동 감지/메뉴 감지 탭 하단 "저장된 기준 이미지" 목록에 미리보기 없이 뜨는 항목이 있다고 제보 —
삭제 버튼을 눌렀을 때 생기는 것 같다고 함. 실제 버그였음.

- **버그였던 것**: `raid_clear_templates`는 전원이 서로의 등록 항목을 볼 수 있는 공용 테이블인데(다른
  사람 화면 배치가 다를 수 있어 자기 게 아니면 실제 인식엔 안 쓰지만, 목록엔 다 보임), 이 목록의 "삭제"
  버튼이 **누가 등록했는지 상관없이 전부에게 노출**되고 있었음. 클릭하면 `deleteRaidClearTemplate`이
  스토리지 파일부터 지우고 DB 행을 나중에 지웠는데, 스토리지 삭제 정책(`raid_clear_template_files_delete`)
  은 로그인한 사람이면 누구나 지울 수 있게 열려 있는 반면 DB 행 삭제 정책(`raid_clear_templates_delete_own`)
  은 만든 사람(`created_by`)만 가능함. 그래서 남이 등록한 항목을 지우려고 하면: 스토리지 파일은 진짜로
  삭제되고, DB 행 삭제는 RLS에 걸려 **에러 없이 조용히 0행 삭제로 끝남** — 결과적으로 파일은 없는데 DB
  행만 영구히 남아 모두에게 "미리보기 없음"으로 계속 보이는 더미 항목이 생김.
- **바뀐 것**(`src/app/actions.ts`의 `deleteRaidClearTemplate`): 삭제 전에 `created_by === user.id`인지
  먼저 확인해서 아니면 명확한 에러("본인이 등록한 기준 이미지만 삭제할 수 있어요")를 던지고 아무것도 안
  지우게 함. 그리고 순서도 DB 행을 먼저 지우고 스토리지 파일을 나중에 지우도록 뒤집었음 — 혹시라도 스토리지
  삭제가 실패해도(네트워크 등) 화면에서 안 사라지는 더미 행보다는 안 쓰는 파일이 스토리지에 좀 남는 쪽이
  훨씬 낫기 때문. UI(`ScreenCapture.tsx`)에서도 아예 본인이 등록한 항목에만 "삭제" 버튼이 보이게 해서
  헷갈리지 않게 함(서버에서 막아도, UI에 버튼이 보이면 눌러보고 에러를 받는 것 자체가 불친절함).
- **기존에 생긴 더미 행 정리**: 코드만 고쳐서는 이미 생겨버린 더미 행이 없어지지 않아서, Supabase SQL
  Editor에서 한 번 실행할 정리 쿼리를 사용자에게 전달함(스토리지에 실제 파일이 없는 `raid_clear_templates`
  행을 `storage.objects`와 대조해서 찾아 지움 — Supabase Storage 메타데이터가 Postgres 테이블로도 있어서
  Storage API 없이 순수 SQL로 판별 가능).

### "기준 영역 등록" 목록에 친구들 것까지 다 보이던 것 → 본인 것만 보이게

- **문제**: `raid_clear_templates`가 전원이 서로 볼 수 있는 공용 테이블이라, 자동 감지/메뉴 감지 탭 하단
  "기준 영역 등록" 목록에 내가 등록한 것뿐 아니라 친구들이 등록한 것까지 다 같이 떠서 헷갈린다는 피드백.
  (참고: OCR 인식 자체는 이미 본인이 등록한 것만 쓰고 있었음 — 화면 해상도/배치가 사람마다 달라서 실제
  인식 좌표를 고를 때는 `created_by === user.id`로 걸러져 있었고, 단지 화면 목록에만 다른 사람 것까지
  같이 보이는 게 문제였음.)
- **바뀐 것**: 두 페이지의 `raid_clear_templates` 쿼리 자체에 `.eq("created_by", user.id)`를 추가해서
  아예 본인 것만 서버에서 가져오도록 바꿈(기존엔 전체를 가져온 뒤 화면 표시는 그대로 두고 인식 좌표 선택
  로직에서만 걸러냈음). 그 결과 región 선택 로직(`resultScreenOcrRegion` 등)의 `t.created_by === user.id`
  조건도 이제 항상 참이라 불필요해져서 같이 정리함. DB에 저장된 기존 등록 내용은 전혀 안 건드림 — 그냥
  "누구 걸 보여줄지"만 바뀐 거라 본인이 등록해둔 영역은 그대로 다 남아있음.

### "숙제 등록했는데 새로고침해야 보임" 버그 원인 규명 및 수정

- **원인**: Next.js Server Action에서 `revalidatePath`를 호출하면 그 경로의 서버 캐시뿐 아니라 클라이언트
  라우터 캐시(다른 탭을 갔다가 돌아올 때 다시 fetch 안 하고 재사용하는 캐시)도 같이 무효화된다. 그런데
  `setCharacterRaids`(숙제 저장)를 비롯해 `importCharacters`, `setMainCharacter`, `refreshAllCombatPower`,
  `resetAllCombatPower`, `toggleGoldEarner`, `deleteCharacter`까지 캐릭터 관련 액션 대부분이 `/`와
  `/characters`만 재검증하고 **`/party`는 빠져있었음**(유일하게 `reorderCharacters`만 세 경로 다 챙기고
  있었음 — 이전에 누군가 이 문제를 겪고 그것만 고쳤던 흔적으로 보임). 그래서 숙제를 등록/캐릭터를 바꾼
  직후 대시보드 화면 자체는 클라이언트 상태로 바로 반영되는데(눈에는 정상으로 보임), 그 뒤 다른 탭에
  갔다가 "공격대" 탭으로 돌아오면 라우터 캐시가 무효화 안 된 그 탭은 변경 전 스냅샷을 그대로 보여줬음 —
  진짜 새로고침(F5)을 해야만 서버에서 다시 받아오니 그제서야 반영된 것처럼 보인 것. "가끔씩"이라고 느껴진
  이유는 바로 그 탭으로 돌아올 때만 재현되고, 같은 화면에 계속 머물면 문제가 없었기 때문.
- **바뀐 것**: 위 7개 액션 전부에 `revalidatePath("/party")`를 추가함. `setRaidCheck`(체크/해제)는
  일부러 `revalidatePath`를 안 쓰고 Realtime 구독으로만 반영하도록 되어 있는데(연속 호출 시 렌더링이
  깨지는 문제 때문 — 주석에 이미 기록돼 있었음), 이건 그대로 손대지 않음.

### 등록한 기준 영역을 다른 친구들에게 "예시"로 공개하는 기능 추가

- **바뀐 것**: `raid_clear_templates`에 `is_example` 컬럼을 추가하고, 본인이 등록한 항목마다 "등록 예시로
  공개" 버튼을 달아서(자기 것만 토글 가능 — `raid_clear_templates_update_own` RLS 정책 신설) 켜두면 그
  이미지가 자동 감지/메뉴 감지 탭 상단에 "등록 예시" 갤러리로 전원에게 노출됨. 저장되는 이미지 자체가
  이미 딱 잘라낸 크롭본이라(전체 화면에 테두리를 그려 보여주는 방식이 아님) 그대로 보여주기만 하면 "이렇게
  잘라야 한다"는 예시가 됨 — 별도로 사각형을 그려 합성하는 처리는 필요 없었음.
- **DB 스키마 변경 있음 — `migration_2026-08-25_template_examples.sql`을 Supabase SQL Editor에서 실행
  필요**(schema.sql에도 반영해둠).

### "대시보드에서도" 숙제 안 보이는 문제 — 진짜 원인은 Realtime 경쟁 조건이었음

`/party`에 `revalidatePath`가 빠져있던 걸 고쳤는데도 `/`(대시보드) 자체에서 여전히 재현된다는 재확인을
받고 다시 조사함. `/`는 `revalidatePath("/")`가 이미 호출되고 있었고 로컬 상태도 즉시 갱신되는데, 그래도
가끔 사라지는 건 캐시 문제가 아니라 Supabase Realtime 쪽 경쟁 조건이었음.

- **원인**: `setCharacterRaids`(숙제 저장)가 기존엔 그 캐릭터의 `character_raids`를 전부 delete한 뒤
  선택한 것 전부를 다시 insert했음. 그런데 보통 레이드 10개 중 1~2개만 바뀌고 나머지는 그대로인 경우가
  많아서, **안 바뀐 레이드까지 delete+insert가 다시 일어남**. `Dashboard.tsx`의 Realtime 구독은 이
  delete/insert를 각각 별도 이벤트로 받아서 `characterRaidMap`을 갱신하는데, 저장 직후 로컬 상태는
  낙관적으로 이미 정확하게 바뀌어 있는 상태에서, 네트워크 타이밍상 "안 바뀐 레이드를 지운" delete
  이벤트가 뒤늦게 도착하면 그 핸들러가 `(character_id, raid_id)` 키만 보고 지워버려서, 방금 저장했고
  실제로는 그대로 유지돼야 할 레이드가 화면에서 사라짐 — 다음 갱신(새로고침)이 있어야 서버에서 다시
  정확한 값을 받아와 복구됐음. "가끔씩"으로 보인 이유는 이 이벤트 도착 순서가 매번 다르기 때문.
- **바뀐 것**(`src/app/actions.ts`의 `setCharacterRaids`): 전체 delete+insert 대신, 실제로 빠진 레이드만
  delete하고 나머지는 upsert하도록 바꿈 — 안 바뀐 레이드는 애초에 delete 이벤트 자체가 안 생기므로 경쟁
  조건 자체가 사라짐. upsert가 이미 있는 행에 대해 내부적으로 UPDATE를 시도하므로, `character_raids`에
  없던 update RLS 정책(`character_raids_update_own`)을 추가했고, `Dashboard.tsx`의 Realtime 구독에도
  UPDATE 이벤트 핸들러를 새로 추가함(기존 INSERT 핸들러와 동일한 로직 — 이미 선택된 레이드의 골드 받기
  값만 바뀔 때 INSERT가 아니라 UPDATE로 오기 때문).
- **DB 스키마 변경 있음 — `migration_2026-08-25b_character_raids_update_policy.sql`을 Supabase SQL
  Editor에서 실행 필요**(schema.sql에도 반영해둠).

### 파티원 목록 캐릭터 이름 OCR — 빨간 체력바 전용 대비 처리 추가

- **배경**: 자동 감지 탭에서 읽는 "파티원 목록 맨 위(항상 내 캐릭터)" 이름이 빨간 체력바 위에 흰 글씨로
  떠 있는데, 이름이 길어질 수 있어서 가로로 넓게 크롭을 잡아둔 상태라(줄일 수 없음) 인식이 잘 안 되는
  경우가 있다는 피드백. 기존 `enhanceContrast`는 일반 휘도(밝기) 기준이라, 빨간 배경도 R 채널이 높아서
  밝게 잡히고 체력바 자체의 그라데이션·하이라이트 때문에 밝기가 위치마다 들쭉날쭉해 대비가 흐려지는
  문제가 있었음.
- **바뀐 것**(`src/lib/ocrMatch.ts`): "빨간 배경은 G·B가 항상 낮고, 흰 글씨는 R·G·B가 다 높다"는 색
  조합을 이용하는 전용 대비 함수 `enhanceContrastWhiteOnRed`를 추가함 — 휘도 대신 G·B 중 더 작은 값을
  기준으로 삼아서 R 채널의 흔들림(체력바 밝기 변화)에 안 흔들리게 하고, 마지막에 반전해서 Tesseract가
  더 잘 읽는 "밝은 배경 위 어두운 글씨"로 내보냄. `recognizeRegionText`/`cropRegionForOcr`에
  `colorHint?: "whiteOnRed"` 파라미터를 추가해서 선택적으로 쓸 수 있게 하고, `AutoDetectRunner.tsx`의
  파티원 이름 인식 호출에만 적용함(메뉴 감지 쪽 캐릭터 이름은 다른 배경이라 그대로 둠).

### 로아 도구 > 보석 가격 탭 추가

- **경매장 vs 거래소**: 겁화/작열의 보석은 더보기 효율에서 쓰는 파괴석류(거래소=markets)와 다르게
  "경매장"(auctions) 아이템임을 조사 과정에서 확인함 — 장비처럼 매물마다 랜덤 옵션(어떤 스킬에 붙는지)이
  붙어서 "고정 아이템 하나에 시세 하나"가 아니라 매물 목록으로 나옴. 경매장 카테고리 코드 체계도 거래소와
  달라서(보석=210000), `GET /auctions/options`로 따로 확인해서 찾음. `src/lib/lostark.ts`에
  `searchAuctionLowestBuyPrice(itemName)`을 추가 — 이름이 정확히 일치하는 매물 중 즉시구매가 있는 것만
  모아 최저가를 반환함(입찰만 가능한 매물의 BuyPrice=0은 걸러냄).
- **과거 시세 통계가 없다는 제약**: 거래소 아이템은 API가 자체적으로 전일 평균가(YDayAvgPrice)와 최근 14일
  일별 평균(Stats)을 주는데, 경매장 아이템은 현재 매물 목록만 주고 과거 통계를 전혀 안 줌. 사용자가 원한
  "하루 평균가/전일 대비/7일 추이"를 만들려면 우리가 직접 시계열 데이터를 쌓아야 한다는 걸 미리 알리고,
  "현재가 갱신을 누를 때마다 그 시점 스냅샷을 기록해서 점진적으로 쌓아간다"는 방향으로 사용자 확인을 받음
  (당장 완전한 그래프를 만들 방법이 없어서 크론잡 등 다른 옵션도 함께 제시했지만, 기존 더보기 효율의
  "수동 갱신" 패턴과 일관되게 클릭 시점마다 기록하는 쪽을 선택함).
- **바뀐 것**: `gem_price_snapshots` 테이블(gem_key, price, recorded_at)에 갱신할 때마다 6종 보석의
  최저가를 한 행씩 append함. `/api/lostark/gems`는 GET(최근 8일치 기록만 읽음, API 호출 없음 — 자동
  로드해도 부담 없음)과 POST(경매장 API를 실제로 호출해서 스냅샷 추가, 갱신 버튼 전용)로 분리해서
  더보기 효율/시세 캐시와 같은 패턴을 유지함. `GemPrices.tsx`에서 저장된 스냅샷을 브라우저에서 요일별로
  묶어 오늘/어제 평균, 전일 대비(현재 최저가·오늘 평균 각각), 7일 추이를 계산함 — 별도 차트 라이브러리
  없이 인라인 SVG로 간단한 선 그래프를 직접 그림(데이터 없는 날은 이어지지 않고 끊어서 표시).

  갱신했거나 그래프에 2일 미만)은 "데이터 수집 중"으로 표시해서 0이나 빈 값으로 오해하지 않게 함.
- **DB 스키마 변경 있음 — `migration_2026-08-26_gem_price_snapshots.sql`을 Supabase SQL Editor에서
  실행 필요**(schema.sql에도 반영해둠).

### 보석 가격 탭 — 배치 순서 수정 + 3시간마다 자동 기록

- **배치**: 카드 그리드가 3열이라 "8겁화/8작열/9겁화, 9작열/10겁화/10작열"처럼 레벨이 줄마다 어긋나 보였음.
  `GEMS` 배열 순서(8겁화·8작열·9겁화·9작열·10겁화·10작열) 자체는 이미 레벨 쌍으로 돼 있었어서, 그리드를
  2열로만 바꿔서 레벨별로 한 줄씩 나오게 함(원인은 배열 순서가 아니라 열 개수였음).
- **자동 기록**: "현재가 갱신"을 매번 직접 눌러야 하는 게 번거롭다는 피드백으로, 페이지를 안 열어놔도
  3시간마다 자동으로 스냅샷이 쌓이게 함. Vercel Hobby 요금제의 Cron은 하루 1번으로 제한돼 있어서(더 짧은
  주기는 배포 자체가 거부됨) 대신 GitHub Actions 스케줄러를 씀(무료, 사용자가 선택).
  - `/api/cron/gem-prices`(POST) 라우트를 새로 만듦 — 로그인 세션이 없는 외부 호출이라 `CRON_SECRET`
    베어러 토큰으로 막고, DB 쓰기는 로그인 세션 대신 `SUPABASE_SERVICE_ROLE_KEY`(RLS를 전부 무시하는 키,
    이 라우트에서만 씀)로 함. `src/lib/supabase/serviceRole.ts`에 이 클라이언트 생성 함수를 분리해둠.
  - `.github/workflows/gem-price-cron.yml` — 3시간마다 그 라우트를 호출. 저장소 시크릿(`APP_URL`,
    `CRON_SECRET`)과 Vercel 환경 변수(`SUPABASE_SERVICE_ROLE_KEY`, `CRON_SECRET`) 설정이 필요 — 자세한
    절차는 README의 "보석 가격 자동 수집 설정" 섹션에 정리해둠. 설정 안 해도 앱은 정상 동작하고 자동
    기록만 안 될 뿐이라 필수는 아님.
  - **버그였던 것**: `.gitignore`의 `.env*` 패턴이 실제 비밀값이 든 `.env.local`뿐 아니라 커밋해야 할
    템플릿 파일 `.env.local.example`까지 같이 무시하고 있어서, 그동안 이 파일이 한 번도 git에 커밋된 적이
    없었음(README가 참조하는 파일인데 실제로는 저장소에 없었던 것). `!.env.local.example` 예외를 추가해서
    이번에 처음으로 실제 커밋함.

### `/api/cron/*`가 로그인 미들웨어에 막혀 있던 버그

배포 후 실제로 `/api/cron/gem-prices`를 curl로 테스트해보니 307로 `/login`으로 리다이렉트됨 — 미들웨어의
블랭킷 인증 보호(`PUBLIC_PATHS`에 없는 모든 경로는 로그인 세션 없으면 `/login`으로 보냄)가 이 경로도
그대로 막고 있었음. 이 라우트는 애초에 로그인 세션이 아니라 `CRON_SECRET` 베어러 토큰으로 자체 인증하는
구조라 미들웨어의 세션 체크가 필요 없음(오히려 방해가 됨). `PUBLIC_PATHS`에 `/api/cron`을 추가해서 미들웨어
단계는 건너뛰고 라우트 자체의 시크릿 검증만 거치게 함.

## 새 세션에서 작업 재개할 때 체크리스트

1. 이 파일과 [README.md](../README.md)를 먼저 읽기
2. `git log --oneline -20` 으로 최근 커밋 확인 (커밋 메시지가 곧 변경 이력)
3. 로컬에서 코드 수정 시: PowerShell 새 명령마다 PATH 재설정 필요
   (`$env:Path = [System.Environment]::GetEnvironmentVariable("Path","Machine") + ";" + ...`)
   — 셸 상태가 명령 간 유지되지 않아서 매번 필요함
4. 수정 후 `npm run build` + `npm run lint` 통과 확인 → git commit → GitHub push (Vercel 자동 재배포)
   — GitHub push용 Personal Access Token은 매번 사용자에게 새로 요청 (저장 안 함)
5. DB 스키마를 바꿨다면 `supabase/migration_YYYY-MM-DD_설명.sql` 새로 만들고, 사용자에게 Supabase SQL
   Editor에서 실행해달라고 안내 (직접 실행할 방법 없음, service_role 키를 매번 새로 받지 않는 이상)
